Why it exists

Not a design kit. Not a black-box platform.

Most teams end up choosing between generic component libraries and oversized finance systems that dictate too much architecture. FinEngine is meant for the middle ground: explicit financial logic, packaged cleanly, with room for product teams to build around it.

What the name signals

Fin keeps the category immediate. Engine makes the promise narrower and more credible: structured logic, repeatable outputs, and software that prioritizes correctness over spectacle.

Module architecture

A practical package surface

@finengine/core

Shared types, money primitives, validation guards, rounding rules, and domain contracts that other packages can depend on.

@finengine/math

Amortization schedules, APR helpers, XIRR, fee ladders, penalties, tax rules, and cashflow routines.

@finengine/ui

Repayment tables, amount fields, statement blocks, and finance-specific interface patterns that stay compatible with existing apps.

@finengine/pay

Payment formatting, QR payload helpers, merchant display logic, and integration-friendly validation utilities.

@finengine/reporting

Statement schemas, export-friendly record shapes, and report primitives for internal review and customer-facing outputs.

@finengine/ledger

Journal entry helpers, account mapping conventions, and reconciliation-friendly structures for transaction systems.

Operating principles

Useful to developers. Defensible to operations.

  • Deterministic first. If two environments run the same logic, the outcome should match.
  • Traceable by design. Financial outputs should be explainable to reviewers, not just beautiful in demos.
  • Modular adoption. Teams should be able to start with one package instead of buying a full stack upfront.
  • Stable interfaces. Finance code gets reused across dashboards, workflows, and exports. Stability matters more than novelty.

Adoption path

Start small, keep the core stable

Phase 1 — utility adoption

Ship the math and validation packages first. Let product teams keep their current UI and backend choices.

Phase 2 — reporting and controls

Add structured exports, statements, and reconciliation workflows once the financial model is trusted in production.

Repository setup

Prepared for Pages and JS.ORG

Public site

This repository is designed to publish as a static documentation home on GitHub Pages first, then move under a JS.ORG domain once the content is live and substantive.

Brand usage

Use FinEngine as the product name and FinEngine Labs as the legal or company wrapper when needed for formal documents.

Working assumptions

Early documentation should answer three questions clearly: what problem the package solves, which financial rules it encodes, and how a team can verify results when they integrate it.
